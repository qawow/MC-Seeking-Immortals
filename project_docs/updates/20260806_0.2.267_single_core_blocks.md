# 0.2.267 single_core 站点核心方块（主线开局解堵）

## 更新内容

排查「物品获取 / 主线 / 多方块」三个方向后，发现它们卡在同一个根因上，本批先解这一处。

### 一个两行的映射表

`MultiblockStationService.java:29-31`：

```java
Map.of("low_spirit_iron_ore", ..., "yin_essence_ore_block", ...)
```

只有 2 条。但 `multiblock_station_patterns.json` 里有 **13** 个站点用 `pattern.validator == "single_core"`。其余 11 个走到 `:305-309`，返回 `missing_core_mapping`，`isStationFormed` 永远为 false —— 不是难成型，是**不可能**成型。

### 后果落在主线开局

`DetailedQuestProofService.java:1103` 的结构证明要求 `isStationFormed` **且** `isCommissioned`。而：

- `mortal_qixuan_entry` 第 5 步要 `contribution_stele` 成型
- `huangfeng_blood_quota` 第 1 步要 `inner_sect_task_board` 成型

这是第 0-1 章。正常生存流程走不到第二章。

我核过全部 8 条 `STRUCTURE_FORMED` 路由，只有这 2 条是硬堵的；另外 6 条用 `teleport_gate`、`cultivation_chamber`、`small_control_2x2`、`rift_world_seed`、`secret_realm_gate`，这些验证器都已实现。

链路其余环节本来就是通的：放方块 → `isStationFormed` 为真 → `catalog station form` 付材料 → commissioned → `MultiblockOperationalService.java:346` 调 `recordStructureFormed` → 证明落账。缺的只有第一环。

### id 冲突与取舍

这 11 个 id 已作为 bulk 目录载体存在（有物品，无方块）。按选定策略：注册同名方块 + BlockItem，并从 `catalog_bulk_items.json` 摘除该 id（1202→1192）。方块注册表与物品注册表是分开的，所以冲突只发生在 BlockItem 与 bulk 物品之间。

`ModBulkItems` 新增 `BLOCK_OWNED_IDS` 兜底：将来目录再生若把某个 id 写回来，会被跳过并打警告，而不是在注册阶段崩掉游戏。

### 一个必须留下的例外

`structure_blueprint_table` **不接方块**。它经 `BaseMaterialItem.java:60` → `StructureToolService.java:35` 作手持工具用，正是 0.2.232 那套投影建造引导的入口。给它 BlockItem 会把右键从「开投影引导」变成「放方块」—— 而且不报错、不崩、不失败任何测试，只是功能静默死掉。测试里把这一条例外具名钉住，并断言例外集大小为 1，防止将来悄悄扩大。

### lang 是新增而非迁移

我原本打算把 `item.seeking_immortals.*` 改成 `block.*`。查证后否掉了：有 **14 处** Java 在运行时拼 `"item.seeking_immortals." + id`（`ManualCatalogService`、`ArtifactOwnershipService`、`FlightVehicleService`、`SummonHonestMvpService` 等）。删掉 item 键会让这些目录 UI 显示裸键字符串。所以两个键都留，中英各 5734→5744。

### 贴图

先改 `generate_block_textures.py` 的推断表再跑，否则 9 个方块会按默认落到灰砖 —— 一块矿石、一块任务牌、一个丹柜长得一样。新增 `SINGLE_CORE_ORES` / `SINGLE_CORE_WORKSTATIONS` 两组规则：宗门木器→wood，`ice_crystal_cooler` 与 `spirit_vein_tap`→jade，`kunwu_copper_ore`→bronze。

同时删掉这 10 个 id 的 `textures/item/*.png`，让它们退出物品贴图生成器的发现范围（该生成器从 `catalog_bulk_items.json` 读元数据，id 摘除后若贴图还在会产生 10 处渲染不一致）。

## 剩余风险

- **构建通过不代表能启动**。所有相关测试读的是源码文本而非活注册表，所以重复物品 id 能过整套构建，只在游戏启动时崩。我把 BlockItem 注册与 bulk 摘除放在同一批，并加了 `BLOCK_OWNED_IDS` 兜底，但这一条只能靠实机启动一次来证明。**尚未实机验证。**
- **旧存档里的这 10 个物品**会解析成 `BlockItem` 而不是原来的目录载体物品。不掉物品、不报缺失，但目录载体写过的 NBT 会被忽略，且任何 `instanceof CatalogCarrierItem` / `BaseMaterialItem` 的分支对这些 id 不再命中。
- `contribution_stele` 与 `inner_sect_task_board` 在作者数据里标的是 `1×1×2`（`size.h=2`），但 `single_core` 只校验 `origin` 一格。放一块就算成型 —— 相对作者规格是抄了近路。
- `kunwu_copper_ore` 注册成了矿石，但**没有任何 worldgen**（无 configured_feature / placed_feature / biome_modifier），所以只能创造模式拿或手放，挖不到。目前没有任务步骤要求挖它，但作为「矿石」是名不副实的。
- 这 10 个 id 从 `ItemCatalogService.carriers()` 消失了（该 map 只从 bulk JSON 构建），所以它们的 grade/category 元数据没了。当前这 10 个都是 `material` 且无 grade，故无行为损失。
- `reference/text_material_id_map.json` 里这 10 条仍标 `canonical_type: "item"`。语义上是个瑕疵，但 `JsonSanityTest` 的 `allowedTypes` 没有 `"block"`，改它是另一件更大的事。
