# 0.2.269 符箓配方数据驱动化（19 种成品从无路可造到可造）

## 更新内容

上一批把符箓**供给**补通了。这一批解开真正的假覆盖：作者的 24 条符箓配方从未被读过。

### 两份互不相干的 24

`talisman_recipes.json` 有 24 条配方、**24 种不同成品**。`TalismanCraftService.buildRecipes()` 另有一份硬编码的 24 条，只产出 **5 种**成品（`fire_talisman` / `armor_talisman` / `speed_talisman` / `yin_body_protection_charm` / `pressure_resist_charm`），靠重复指向凑够条数。

两份只有 5 个 id 重合。作者的 19 种符箓在制符台上没有任何入口。

### `return 24` 把缺口盖住了

```java
public static int recipeBlueprintCount() {
    return 24;
}
```

四处断言钉这个数（`CraftCatalogCoverageTest:14`、`M04CraftProductionTest:81`、`JeiRecipeCoverageResourceTest:66`，另有一处 `> 0`）。它们全都通过，而且**永远**通过 —— 硬编码列表和作者语料哪一边变了都不会被发现。现在该方法数作者语料，作者加一条配方，四处断言同时跟着动。

### 落地时兑现了三个此前被丢掉的作者字段

- **`yield`**：作者按品阶给 1-3 产量（21 条可造配方里 10 条 >1，走满一轮共 33 张）。旧代码恒定 `new ItemStack(product)`，即恒定 1。
- **`ink`**：作者给**每条**配方指定专属符墨（妖血墨 / 灵草墨 / 精魄墨）。旧代码给所有 24 条强制扣 1 个 `talisman_ink_bottle` —— 这正是上一批查到的「符墨零来源导致整套符箓在数据层关闭」那一条。现在按配方自己的 `ink` 字段扣，而三种墨的配方上一批已落成。
- **`realm_min`**：作者按 QI_REFINING / FOUNDATION / CORE_FORMATION / NASCENT_SOUL 分档。旧代码完全没有境界门槛。新的 `realm_too_low` 关卡排在扣材料**之前**，所以低境界玩家不会先付料再被拒。

### 3 条 stub 故意不可造

`recipe_invisibility_talisman`、`recipe_binding_talisman`、`recipe_gold_armor_talisman` 在作者语料里只有 `paper_grade` / `ink` / `base_success_rate`，**没有 materials 数组**。我没有替作者编材料：这三条计入蓝图数（24），但运行时按 fail-closed 跳过，`recipes()` 实际给出 21 条。测试把这三个 id 具名钉住，并断言它们**不得**长出 materials —— 哪天作者补了材料，测试会要求把它们移出 stub 集合放开制作，而不是默默接受。

### 收割口径同步

制符现在是**真实发放渠道**了。`TalismanSupplyChainResourceTest.grantPositions()` 加了这一渠道：每条带 materials 的蓝图发放它的 `talisman_id`。不加这一条，下次统计又会把 21 种新可造符箓算成「无获取途径」—— 和上一批我漏掉四个渠道是同一类错。

## 验证结果

- 新增 `TalismanAuthoredRecipeTest`（5 项，已核对 `TEST-*.xml` 确认真实执行）。**先失败后修复**：首个断言针对 `ModItems.TALISMAN_PAPER_MORTAL` 硬编码，修前在 `TalismanAuthoredRecipeTest.java:22` 报 `AssertionFailedError`。
- 该测试钉住六件事：配方不得硬编码在 Java、`recipeBlueprintCount()` 不得是字面量（正则查 `recipeBlueprintCount() { return 24`）、蓝图数必须等于语料条数、24 种成品必须互不重复（重复即有成品不可达）、每条可造蓝图必须有 materials 与 ink、`yield` 与 `realm_min` 必须真正到达运行时。
- 墨与境界的取值集合也钉住（三种墨、四档境界），改动作者语料会要求同批确认每个新值都能解析、每种新墨都有获取途径。
- `TalismanCraftServiceTest` 随 `preflightFailure` 签名从 3 参改 4 参更新，并新增一条断言：境界不足时报 `realm_too_low` 而非 `missing_materials`，即关卡顺序为 技能 → 境界 → 材料。
- 顺手统一了 `craftById`：删掉它自己那道提前的材料检查，改为和制符台走同一处 preflight，两条入口的失败原因与顺序不再可能分叉。
- 旧的 5 种成品没有因此丢失获取途径 —— 逐个核过，五者都另有配方或商店发放位。
- 定向：`craft.*`、`catalog.*`、`compat.jei.*`、`JeiRecipeCoverageResourceTest`、`TalismanSupplyChainResourceTest`、`MultiblockOperationalServiceTest` 全部通过。
- lang：新增 `talisman_table.realm_too_low` 一键，中英各 5744→5745，完全对等，无单侧键。
- 生成器：按 `spell -> visual` 顺序刷新并 `--check` 通过；profile 数 2292/5733 零变化，视觉两文件仅 `source_hashes` / `java_source_audit` 各 1 行变动；方块与物品贴图 render_mismatch 与 uniqueness_adjustments 均为 0。

## 剩余风险

- **未实机验证**。全部断言读的是源码文本与语料 JSON，制符成功率、产量手感、境界门槛卡点都没在真实客户端走过一次。
- **21 种成品刚变成可造，但它们的施放行为是 role 推断的**。24 个成品在 `talisman_catalog.json` 里都有 `role`，经 `CatalogTalismanService.resolveMode` 映射到投射/护体/遁逃等模式 —— 也就是说「锁魂符」和「散魂符」可能走同一个 mode。能用，但不是逐符定制的效果。
- **成功率没有按符纸品阶加成**。作者在 `talisman_materials_catalog.json` 给每种符纸标了 `success_base` 与 `effect_mult`（凡符纸 0.7 / 下品 0.8 / 中品 0.9…），我只用了配方自己的 `base_success_rate`，纸的品阶差异未参与计算。相对作者规格抄了近路。
- **`paper_grade` 与 `paper_item_id` 未交叉校验**。我按 materials 数组扣料，而作者另有 `paper_item_id` 字段声明纸张。当前 24 条里两者完全一致（已核对），但没有断言钉住它，将来作者改一处不改另一处不会被发现。
- **3 条 stub 仍不可造**，`invisibility_talisman` / `binding_talisman` / `gold_armor_talisman` 三种成品因此仍无任何获取途径。这是作者数据缺失，不是代码缺陷；等作者补材料，或另开一批按同族配方比例补齐。
- **`talisman_ink_bottle` 现在没有任何配方消费它**。上一批为它落了配方（因为旧代码强制扣它），这一批改成按作者的三种墨扣料后，它变成一个可造但无用途的物品。没有破坏任何东西，但语义上悬空了。
