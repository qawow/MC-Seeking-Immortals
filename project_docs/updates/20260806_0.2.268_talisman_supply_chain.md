### 符箓系统在数据层是关闭的

28 项符箓链输入里 19 项无获取途径，过了别名解析仍是 19/19。最要命的一条：`TalismanCraftService.materialRequirements:201` 给**每一条**符箓配方强制附加 1 个 `talisman_ink_bottle`，而符墨自身零来源。也就是说整套符箓制作在数据层就是关闭的，不管配方怎么写。

### 缺口为什么一直隐形

商店条目的 `id` 只是标签，`item` 才是实发物（`ShopService.java:626`）。而：

- `tiannan_talisman_lane` 有一条 `{"id": "talisman_paper", "item": "...talisman_paper_mortal"}` —— 标签叫「下品灵符纸」，实发**凡符纸**。
- `tiannan_refinement_forge` 有一条 `{"id": "low_spirit_iron", "item": "...spirit_iron"}` —— 标签叫「低阶灵铁」，实发**灵铁**。

两处都让人以为有卖，扫一眼 grep 也会命中，但那个 id 本身拿不到。

墨同理：按 `materials_catalog.json` 的 `craft_from` 落成妖血墨、灵草墨、精魄墨三条，外加符墨瓶。`beast_blood_ink` 的两个原料（妖兽血、灵石碎片）本来就能拿到，只差配方。

### 我的收割四次漏渠道

「55」这个数字最初是虚高的。每次都靠测试自带的健全性断言或和 Python 对账发现：

1. 炼丹产出字段是 `output_items`，键为 low/medium/high/**supreme**，不是我写的 `outputs`。是测试里 `assertTrue(obtainable.size() > 300)` 报「grant harvest looks broken: 281」抓出来的。
2. `worldpack/boss_loot_runtime.json` 是真实发放渠道 —— `BossLootService.java:154` 先读它，作者的 `text_material/boss_loot_tables.json` 只是文件缺失时的回落。补上后 20 → 10。
3. `SpiritStoneLadderService.java:112` 的元素兑换链能把下品金灵石换成中品，所以 `metal_spirit_stone_mid` 本就可得，没有数据文件会列出它。
4. 妖兽分档掉落 `beast_loot_tiers.json`。

修正后真实数字是 10，再补齐到 0。这四次都是我自己的统计口径错，不是代码问题 —— 记在这里是因为「哪些算发放渠道」这件事本身容易漏，下次改这块要照这五个渠道核。

## 剩余风险

- **价格与掉率是我定的手感值**。作者只给了材料与区域，没给灵石价或掉率。商店价按同店同档物品比价，首领掉率按稀有度分档（common 0.26-0.30、epic 0.07-0.10、legendary 0.05）。实机经济观感未验证。
- **符箓配方仍是硬编码**。`TalismanCraftService.buildRecipes()` 的 24 条只产出 5 种成品，`talisman_recipes.json` 的 24 种成品仍未落地，`recipeBlueprintCount()` 仍是 `return 24`。本批只解供给，下一批才改数据驱动 —— 顺序是刻意的：先补供给再改配方，否则符箓会从「能做」变成「做不了」。
- **`fire_feather` 与 `feather_fire` 中文都显示「火羽」**，是重复物品。前者是作者符箓配方用的，后者有火鸦掉落。本批给 `fire_feather` 加了商店来源，但没有合并这两个 id —— 合并要动别名表与已有掉落，属另一件事。
- `kunwu_copper_ore` 之类的问题这里也有：`turtle_shell` 等挂到首领后只能靠打首领拿，而首领在秘境里，秘境有境界门槛。低境界玩家看得到配方仍做不出，只是从「永远不可能」变成「需要推进度」。
- 基线钉 0 意味着以后**新增配方必须同批补齐原料获取途径**，否则构建失败。这是有意的约束，但会让「先写配方后补材料」的工作流被挡住。
- 造纸阶梯与墨配方都是普通工作台 shapeless，没有走 `talisman_table` 站点。作者数据里写的是 `"station": "talisman_table"`，这一条我没实现 —— 相对作者规格抄了近路。
