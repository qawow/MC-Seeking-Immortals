# 0.2.270 物品获取普查上锁 + 主线唯一制作证明解堵

## 更新内容

本批做两件事：把「哪些物品拿不到」从我的手算变成仓库自检，以及修主线上一条两重堵死的证明路由。

### 先更正我自己的数字

我在 0.2.267 的交接里写过「约 646 个孤儿物品」。**这个数字是错的**，本批实测为 **1128 / 1667**。

错在两处：646 只统计了 bulk 目录物品（漏掉手写注册与枚举派生的分级丹药），且用的「可得」口径比发放位宽。中途我还报过一次 1128 之前的 1073 和 1141 —— 每次都因为收割口径不同。

数字反复错三次，说明它不该由我手算。所以本批把普查落成测试。

### 注册物品的真实全集是 1667

物品注册有三条路径：`ModItems` 的 208 处字面量、7 个 helper 工厂（`registerCatalogPill` 等）、以及 `catalog_bulk_items.json` 的 1192 条。分级丹药按 `type.id() + "_" + suffix` 拼接注册，**源码里根本没有它的 id 字面量**，所以任何按字面量收割的方法都会漏掉它们。

唯一能覆盖全部三条路径的表面是 `models/item/*.json`：1667 个。测试断言 bulk 的每一条都有模型，用来证明「模型集就是注册全集」这个代理关系成立，而不是假定它。

### 17 条发放渠道

除 0.2.268 已知的 8 条外，本批查出并纳入：法宝炼制（`refinement_recipes.json` 73 条）、傀儡组装、主线任务奖励、名义 NPC 掉落、飞升配装、拍卖法宝、炼制失败回收、以及**硬编码发放**（服务里直接 `giveOrEnqueue(new ItemStack(ModItems.X))` 的 54 个 id）。

漏掉硬编码那一条会让 6 个实际可得的物品显示为拿不到 —— 这是测试自己抓出来的：我第一版写完跑出 1134，比手算多 6 个。

排除掉的三条（查证后确认不是发放渠道）：

- `items_by_region.json` —— `RegionItemsService` 与其唯一调用方 `SeekingImmortalsCommand` 的 `giveOrEnqueue` 调用数都是 0，是定价/展示数据。
- `sects/missions/*.json` 的 `item` —— `collect_item` 目标，是**要求**玩家交的，付的是贡献点。
- `beast_materials_loot_v92.json` —— 内容是中文显示名（「兽皮」「兽骨」），不是物品 id，是设计文档。
- `catalog/merchant_shops_runtime.json` —— 只是店铺 **id 列表**，真实货单仍在 `shops/<id>.json`（`ShopService:597`），我原先担心的「runtime 覆盖 authored」在这里不成立。

### 主线唯一的 CRAFT_COMPLETED 路由此前不可能完成

全部 95 条证明路由里只有 **1 条**是 `CRAFT_COMPLETED`：`deity_huoyu_path` 第 6 步「合成回阳真水」。它两重堵死：

1. **id 对不上。** 路由要 `huiyang_true_water`，而名为 `huiyang_true_water.json` 的炼丹配方产出的是 `return_yang_true_water` 及其分级。玩家能拿到的东西永远不等于路由要的 token。
2. **炼丹根本不发制作证明。** 取出成丹只记 `recordAlchemyCompleted(station)`。`recordItemCrafted` 唯一调用点在 `QuestHookRuntime.onItemCrafted`，挂的是原版 `ItemCraftedEvent` —— 那个事件对丹炉不触发。所以任何带物品的制作路由都无法靠炼丹满足。

两处都修：`PROOF_ITEM_MAPPINGS` 加 token 映射（四个分级都算），丹炉取丹时补记实际产出物。废丹不算（失败批次），id 取自实发 stack 而非客户端输入。

### 顺带修了一处既有测试的盲区

`DetailedQuestItemProofRouteTest` 的「真实载体」校验只认 bulk id 与源码字面量，因此把**所有枚举派生的分级丹药**都判为假载体 —— 我加映射时它报 `mapped prover is not a real carrier: return_yang_true_water_supreme`。这是那条断言本身的盲区，不是我的映射有问题：那个 id 确实注册了，只是没有字面量。改成同时识别 `base + PillQuality` 的拼接注册。

### 9 个重复丹药 id：查明但不删

`bigu_pill`（辟谷丹）等 9 个 id 与其分级阶梯重复 —— 商店挂 `id: bigu_pill` 实发 `fasting_pill_low`（下品辟谷丹），又是 0.2.268 那个 `id`/`item` 标签机制。

按用户「冗余的删」策略本应删，但**查证后否掉了**：这 9 个 id 的引用面覆盖 20+ 个数据文件、`ConsumableVfxOrchestrator`、`pill_effect_catalog.json`，其中 `huiyang_true_water` 还被主线证明路由引用。删除风险远大于收益。分级丹药的效果走 `CatalogPillItem` 的 `CatalogPillType` switch，与 `pill_effect_catalog.json` 无关，所以功能上没有损失。留作已知冗余，用商店标签断言钉住。

## 验证结果

- 新增 `ItemAcquisitionAuditTest`（3 项）。**先失败后修复两次**，且都是真实缺陷：第一次报 `1134 > 1128`（我漏了硬编码发放渠道），第二次报商店标签实测 134 而我猜的是 62。
- 三条断言：注册全集必须恰好 1667（变动即要求重新普查）、孤儿数**上限 1128**（补获取会降低它，新增不可达物品会顶破它）、17 条渠道**每条都必须有产出**（某条静默失配会让可得物品显示为不可得 —— 这正是 0.2.268 把死配方数从真实的 10 虚报到 55 的机制，共发生四次）。
- 商店标签断言另钉一条具名项：`market_herbal_stall.json:bigu_pill->fasting_pill_low` 必须仍可见，防止这类别名悄悄消失后无人知晓。
- 新增 `MainStoryCraftProofTest`（2 项）。**先失败后修复**：修前报 `crafting 下品回阳真水 must prove deity_huoyu_path step 6, or the chain is uncompletable`。
- 定向：`quest.*`、`alchemy.*`、`resources.ItemAcquisitionAuditTest` 共 185 项通过。
- 生成器：按 `spell -> visual` 顺序刷新并 `--check` 通过；profile 数 2292/5733 零变化；方块与物品贴图 render_mismatch 与 uniqueness_adjustments 均为 0。
- 完整构建：`./gradlew build --no-daemon --max-workers=1 --console=plain` 成功，`BUILD SUCCESSFUL in 1m 29s`，preflight 记录 `mod_version=0.2.270`。
- 测试总量：**274 套件 / 1,337 项，failure/error/skipped 均为 0**。
- JAR：`seeking_immortals-0.2.270.jar`，SHA-256 `419865c6472dac12243635fcf65355f38af0b4277c9086242d5dbbaedd1e6196`。

## 剩余风险

- **未实机验证**。`deity_huoyu_path` 第 6 步的修复没有在真实客户端炼一次丹走通；断言证明的是映射与调用点存在，不是端到端可完成。该步要 NASCENT_SOUL 境界才能控火，实机验证成本不低。
- **1128 是上限而非目标**。它只保证不恶化。612 个 material、174 个 artifact 孤儿仍无获取途径，这是本批**没有解决**的主体问题。
- **144 个法宝有目录条目但无炼制配方**，且作者数据里没给 materials（只有 `learn_requirements.obtain.source`，且多为 `loot_craft_quest` 或中文散文如「通天灵宝向」）。补它们等于替作者设计配方，不属于「按作者数据落地」。
- **9 个重复丹药 id 仍在**。已查明、已钉住，但没删；`talisman_ink_bottle`（0.2.269 遗留）同样是可造但无用途。
- 丹炉现在每次取丹都会多发一条 `recordItemCrafted`。幂等由 `repeat_policy: IDEMPOTENT` 保证，但这是新增的每次取丹开销，未做性能测量。
- 商店标签上限 134 是**实测当前值**，不是审阅过的目标值。里面多数是刻意的品阶别名（`foundation_pill -> foundation_building_pill_low`），但我没有逐条判定这 134 条是否都合理。
