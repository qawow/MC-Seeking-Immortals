# 0.2.266 QA 前置：拍卖行非管理员入口与请柬声望闩

## 更新内容

给 QA-01 写签字清单前先核查每一步能不能真的跑，结果拍卖那一步跑不了，于是先修缺口。

### 阻塞点

QA-01 要求「完成任务链、对话动作、突破、宗门、拍卖、阴阳窟闭环**不用管理员命令**」。但拍卖行只有一个入口：

- `bid` / `settle` 的唯一授权门是 `AuctionHallMenu`（`AuctionActionPacket:48`，凭 `accessToken` 校验）。
- 打开这个菜单的唯一调用方是 `AuctionSoftService.openHall`，而它的唯一调用点是 `SeekingImmortalsCommand:1742` —— permission 2 的 `catalog auction open`。

也就是说，不开管理员权限，玩家进不了拍卖行。清单按原样写出来会是一条不可执行的步骤。

### 作者其实早就写好了凭证

拍卖请柬（`auction_invitation`）在三处**互相独立**的作者数据里都是拍卖凭证：

- `merchant_shops.json`：乱星海岛杂货售价 30 灵石、库存 5。
- `consumables_index.json` / `consumables_catalog.json`：`effect: open_auction_invite`，category `quest`。
- `spatial_nodes_index.json` 与 `trade_routes.json`：`node_dajin_wanbao` 与 `dajin_wanbao_spine` 的 `requires` 就叫 `auction_invite_or_reputation`。

并且 `shouldConsumeOnSuccess` 早已把 `open_auction_invite` 排除在消耗之外 —— 作者是按「可重复使用的通行证」设计的。

而 `openAuctionInvite` 的实现只有两行：加 2 点 `merchant_guild` 声望，打印一句「可前往拍卖行大厅」的提示。凭证存在，门没接上。

### 同一路径上的第二个缺陷

请柬不消耗、无闩、无冷却，声望却每次右键都发。`ReputationService.add` 也没有上限。所以一枚 30 灵石的请柬可以无限右键刷 `merchant_guild` 声望。

收益不在拍卖：三个场馆的 `rep_min` 都是 0，所以这**不是**拍卖解锁向量。实际收益是 `shopDiscountMultiplier`（FRIENDLY 10 / HONORED 25 两档永久商店折扣）加上 `recordReputationReached` 白送一个声望类任务证明。

### 区域权威的来源

新增 `AuctionSoftService.hostsVenue(regionId)`，合法区域从 `economy_auction_bands.json` 的 `venues[].region` 反推 —— 目前是 `dajin`（万宝拍卖）与 `chaotic_sea`（乱星海内场）。空白与未知区域一律返回 false，起始区域 `qinglan_mountains` 不放行。以后作者往 bands 里加场馆，不改 Java 就能到达。

### 收口方式

`openAuctionInvite` 现在按顺序做三件事：按当前区域校验场馆存在（不存在则提示并返回 false，不发声望不开界面）、以 `AUCTION_INVITE_INTRODUCED_KEY` 持久闩发放一次性引荐声望、`openHall(player)`。

请柬**仍然不消耗**。闩收口的是重复发放，不是玩家的请柬 —— 用「吃掉请柬」来堵刷声望会违背作者的通行证语义。

## 剩余风险

- **旧档已经刷过的声望不会回收**。闩是新加的，之前无限右键攒下的 `merchant_guild` 数值原样保留，对应的永久折扣也保留。我没有写回收逻辑，因为无法区分刷来的和正常玩来的。
- 一次性引荐声望闩在**玩家**身上（`getPersistentData()`），不在请柬上。所以同一玩家换一枚新请柬也不会再拿到引荐声望 —— 这是有意的，但如果作者本意是「每张请柬各算一次人情」，语义就反了。
- `hostsVenue` 只校验区域，不校验玩家是否真的站在拍卖行建筑里。整个 `dajin` 与 `chaotic_sea` 境内任意位置都能开界面，`MenuAccessContext.atPlayer` 的 8 格距离只锁住开界面之后的位移。要更严需要拍卖行方块或 NPC 作为 source 实体。
- 请柬走 `openHall(player)` 单参重载，没有传 source 实体，因此走的是 `atPlayer` 而非 `atEntity`。若以后接入万宝阁 NPC，应改用 `openHall(player, 0, npc)`。
- `node_dajin_wanbao` 的 `auction_invite_or_reputation` 仍只是显示用的需求文案（`SpatialNodeCatalogService:277`），本批没有把持有请柬接成该节点的真实激活条件。
