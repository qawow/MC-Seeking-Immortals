## H8 — EXTREME 走火死亡保留 50% 物品
原 `dropHalfInventory` 把 50% 物品掉到世界，但无 PersistentData 序列化 + 重生归还。keepInventory=true 服下被掉的 50% 永久丢失。
- `BreakthroughService`：EXTREME 分支改调 `preserveHalfInventory` — 把 50% 物品序列化为 ListTag 写入 `player.getPersistentData()["SeekingImmortalsExtremePreserved"]`，**从背包移除但不掉世界**；随后 `hurt(magic, Float.MAX_VALUE)` 死亡（vanilla 此时 keepInventory=false 掉剩余 50%，keepInventory=true 保留剩余 50%）。
- `BreakthroughService.restorePreservedOnRespawn(player)`（public static）：重生时读取 ListTag，`inventory.add` 归还（背包满则 `player.drop` 掉地面），用完即删 key。
- `ModEvents.onPlayerRespawn`：追加调用 `restorePreservedOnRespawn(player)`。
- 删除已无调用方的旧 `dropHalfInventory` 死代码。
- 结果：keepInventory=false → 地上 50% + 重生 50%；keepInventory=true → 重生保留 50%。

## M6 — 灵石 NBT 腐坏防护（守卫方案，不改源码）
经实读：`use()`（SpiritStoneItem:43）、`consumeStoneBonus`（ModEvents:506）、主动吸收路径（ModEvents:694）全程 `getCount()==1` 门控；`consumeStoredPower`（:127-138）的 `count!=1 → return 0` 守卫已达成防 NBT 腐坏核心目标。checklist 原要的 `split(1)+shrink(1)` 多叠吸收方案与单颗灵石使用架构相悖，且 split/merge 存在 NBT 语义陷阱（merge 后 NBT 取栈主、丢 single 已更新 NBT）。
- 本轮决策：守卫方案视为落地——防腐坏目标达成，多叠吸收属设计外行为不启用。**不改源码**，仅勾选 checklist 注明。如后续需多叠吸收，需先重构单颗 NBT 物品叠放模型，单独排期。

## M11 — writeUtf 加长度上界
`SyncCultivationDataPacket.encode` 全部 6 处 `writeUtf(s)` 用默认 32767 上限，无 bounded overload 也无截断。
- 6 处改 `writeUtf(cap(s, N), N)`：realm/stage/specialPhysique/auraNature 用 64，spiritualRoot 用 128，spiritualRootAttributes 用 256。
- 新增私有 `cap(String s, int maxLen)` 截断 helper（null → ""）。
- decode 侧 `readUtf()` 不变（bounded writeUtf 仍以 readUtf 读）。
- 这些值均服务端生成，上界为防御性截断，正常值远小于上界，不影响功能。
